GPO Abuse

If the current principal has edit rights (GenericWrite / WriteProperty / WriteDacl) over a Group Policy Object, an immediate scheduled task or startup script can be pushed to every computer or user in that GPO's scope — often resulting in domain-wide or OU-wide local administrator access.

Enumerate Editable GPOs Abuse with SharpGPOAbuse Alternative: PowerView Immediate Task

Policy changes only take effect on hosts within the GPO's linked OU scope and after a refresh (forced with gpupdate /force or the default ~90–120 minute client interval). Always confirm scope, security filtering and WMI filters before relying on this technique against a specific host.

Example: Three-Host Domain Chain

Fictional authorized lab walkthrough (domain CORP.LOCAL): WEB01 (10.10.10.21, DMZ) is reached through a SQL injection, a PowerShell history leak leads to APP02 (10.10.20.22, internal segment), a local escalation on APP02 exposes a service account valid on APP03 (10.10.30.23) that already holds directory replication rights. Two separate pivots are required, since neither APP02 nor APP03 is directly reachable from Kali.

01. WEB01: Initial Access Through SQL Injection

In this fictional lab, the application exposes a SQL injection that leads to command execution in the web service context. SQL injection does not guarantee a shell; the result depends on the database, privileges and application setup.

Open the existing Web → SQL Injection guide 02. WEB01: Establish Host Context

Record identity, privileges, domain and network position. In this lab, the SQLi shell lands as the low-privileged CORP\svc_web service account.

03. WEB01: PowerShell History & Local Escalation

Review the PowerShell history before anything else; it is one of the fastest ways to find leftover administrative activity. Finding a password in history alone does not elevate the current token, so validate the actual local privilege path with the existing Windows PrivEsc material.

Open Windows PrivEsc, including PowerShell History and SeImpersonate checks 04. WEB01: Post-Exploitation & LSASS Assessment

After authorized elevation, reassess the host and handle recovered secrets carefully.

 05. Pivot: WEB01 → APP02

APP02 sits on the internal 10.10.20.0/24 segment, which WEB01 can reach but Kali cannot. This is the first of two pivots in this chain: tunnel through WEB01 before touching APP02 at all.

06. APP02: Connect With the Recovered Credential

Through the WEB01 tunnel, authenticate to APP02 using the fictional svc_backup credential recovered from the PowerShell history.

07. APP02: Local Escalation & APP03 Credential

In this scenario, an authorized local escalation path on APP02 (backup privileges) exposes a credential later used for APP03. Confirm the host's actual privilege findings in the existing Windows PrivEsc section rather than assuming any single artifact elevates you.

Open Windows PrivEsc guidance 08. Pivot: APP02 → APP03 (Internal Subnet)

This is the second pivot of the chain. In this lab, APP02 has a route to APP03 and the domain controller that Kali still cannot reach directly. Start a fresh Ligolo-ng session from APP02, select it and configure the authorized subnet route.

Verify the tunnel route before continuing to APP03.

 09. APP03: Connect Through the Tunnel

After validating the fictional svc_adcs credential recovered on APP02, connect to APP03 through the newly established tunnel.

10. APP03: Verify Replication Rights & Assess the DC

The fictional svc_adcs account already has the required directory replication rights. Local Administrator membership alone does not grant DCSync. Confirm authorization, effective rights and target scope before using the existing procedure.

HTB Forest: Active Directory Writeup

Forest is a Windows domain-controller lab. This walkthrough summarizes the reasoning and privilege path; use it only in the retired Hack The Box machine or another explicitly authorized environment.

01. Reconnaissance & Domain Enumeration

The exposed directory services identify the host as a domain controller. Anonymous domain enumeration reveals the domain context and a useful set of user accounts. Record the domain name and validate each account before selecting an attack path.

02. Check the Kerberos Pre-Authentication Setting

Check the directory flag for accounts that do not require Kerberos pre-authentication. In this lab the finding is svc-alfresco. The query below is read-only and identifies the misconfiguration without requesting ticket material.

Review the Kerberos assessment guide 03. Validate Access & User Proof

After obtaining an authorized lab credential through the platform's own exercise flow, verify the account and its scope before connecting. Keep passwords out of shell history and notes; retrieve the user proof only within the retired machine.

04. Review Group Memberships & Directory ACLs

With authorized domain credentials, inspect the relevant memberships and use BloodHound to review the effective ACL path. In the lab, investigate Account Operators, Exchange Windows Permissions, and the domain object's replication-related rights. The commands below perform directory reads only.

Review BloodHound relationship analysis Review Active Directory ACLs 05. Confirm Impact & Root Proof

If the ACL review confirms replication privileges, document the impact and validate the lab's root proof using the authorized exercise process. This walkthrough intentionally omits commands that alter directory permissions or extract domain credential material.

Key Lessons & Defensive Checks
  • Require Kerberos pre-authentication unless a documented exception exists.
  • Use unique, strong passwords for service accounts and review their privileges.
  • Restrict account-creation and group-management rights to approved administrators.
  • Audit domain ACL changes and replication-right assignments.
  • Alert on unexpected account or group changes and unusual directory replication.

HTB Active: SYSVOL & Kerberos Audit Walkthrough

Active is a retired Windows domain-controller lab. The key lesson is that anonymously readable SYSVOL replication data can expose legacy Group Policy Preferences, while a service account can provide a Kerberos attack surface. Commands below are limited to service discovery, share listing and policy inventory; use them only against the authorized HTB target.

01. Port Scan & SMB Share Discovery

Confirm the domain-controller services and check whether SMB permits an anonymous session. In this machine, the notable share is Replication.

02. Review the SYSVOL Exposure

The share contains replicated Group Policy data, including a legacy Group Policy Preferences XML file. A cpassword value in a preference file is a known insecure storage pattern, not a secure secret. Do not copy, decrypt or reuse the value; report the exposure and treat affected credentials as compromised.

Review domain shares and SYSVOL 03. Assess the Service-Account Kerberos Risk

The lab's exposed preference is associated with the svc_tgs service account. Assess whether service accounts have registered SPNs and whether their passwords meet current policy. Keep the review to directory metadata and authorized configuration checks; this guide does not request or crack Kerberos tickets.

Review SPN enumeration guidance Review Kerberos security checks 04. Validate Impact & Remediate

The intended lab chain demonstrates how legacy GPP secret exposure and weak service-account credentials can lead to domain compromise. Do not use recovered secrets to access systems or extract domain credentials. In an assessment, document the affected policy and account, then ask the domain owner to rotate credentials and remove the insecure preference.

  • Remove passwords from Group Policy Preferences and rotate any exposed credentials.
  • Limit SYSVOL access to the domain's intended authenticated principals.
  • Use long, unique, managed service-account credentials.
  • Monitor anonymous SMB access, SYSVOL reads and unusual service-account authentication.
